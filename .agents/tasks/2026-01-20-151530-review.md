## MongoDB resilience and retry logic

The database connection function in server.js wraps mongoose.connect in a try-catch and distinguishes ECONNREFUSED errors from other connection failures. When MongoDB is unavailable, the server logs troubleshooting instructions specific to the OS (Windows vs Linux/Mac), increments a retry counter, and schedules another attempt after 10 seconds. The retry limit is 5 attempts in development; production behavior is left to the deployment environment. A mongoose disconnection listener triggers the same retry logic, allowing automatic recovery when MongoDB restarts during development.

Index additions on the User model (email, isActive, compound index on both) accelerate common queries but no similar indexes were added to Task, Schedule, or Staff models despite being listed as Priority 2 in IMPROVEMENTS.md.

## Email service graceful degradation

The EmailService constructor checks whether EMAIL_USER and EMAIL_PASSWORD exist before initializing the nodemailer transporter. When credentials are missing, it sets isEmailEnabled to false and assigns transporter to null. All email methods (sendEmail, sendBulkEmails, testEmailService) check isEmailEnabled at entry and return early with an error object rather than attempting to use a null transporter.

The verifyConnection method catches transporter.verify() failures and sets isEmailEnabled to false, then logs helpful troubleshooting tips (App Password, 2FA, firewall). This prevents the "Missing credentials for PLAIN" crash that appeared in the original user request.

## NoSQL injection protection and rate limiting

express-mongo-sanitize middleware is applied globally in server.js after body parsers. It strips $ and . characters from request bodies, query strings, and params, preventing attackers from injecting MongoDB operators like $gt, $ne, or $where. The middleware runs before route handlers, so sanitization is automatic across all endpoints.

Two rate limiters exist: authLimiter (10 requests per 15 minutes) applied to /api/auth routes, and a general limiter (100 requests per 15 minutes) applied globally. Both return error responses with code: 'RATE_LIMIT_EXCEEDED' when triggered. The auth-specific limiter defends against credential stuffing and brute force attacks on login/register endpoints. The implementation is IP-based, so it doesn't distinguish between different users behind the same IP, which can be problematic for offices or universities but is acceptable for this threat model.

Missing: per-user rate limiting (Priority 3 in IMPROVEMENTS.md) and email endpoint rate limiting (mentioned in plan but not implemented).

## JWT security and error codes

The auth controller checks JWT_SECRET length on module load and logs a warning if it's under 32 characters or missing. This doesn't prevent the server from starting but signals a configuration issue early. The generateToken function now returns both the token and expiresIn duration, which is included in login/register responses so the frontend can track token lifetime.

auth.middleware.js catches TokenExpiredError and JsonWebTokenError separately, returning TOKEN_EXPIRED and INVALID_TOKEN codes respectively. It also checks user.isActive and returns ACCOUNT_DEACTIVATED when false, preventing deactivated accounts from using valid tokens. The protect middleware returns NO_TOKEN when no Authorization header exists, USER_NOT_FOUND when the token references a deleted user, and AUTH_FAILED for other JWT errors.

All error responses include success: false, message, code, and timestamp (or expiredAt for TOKEN_EXPIRED). This structure enables frontend error handling based on error codes rather than parsing message strings.

Password validation in validateRegistration middleware requires 8 characters, one uppercase, one lowercase, one digit, and one special character, which is enforced via regex before the user is created.

## Security and auth gaps

CORS configuration allows process.env.FRONTEND_URL and http://localhost:3000, with a warning logged when FRONTEND_URL is unset in production. Requests from unlisted origins are rejected with a CORS error and logged to the console. The implementation prevents accidental exposure but relies on manual origin management rather than pattern-based allowlists.

No refresh token mechanism exists—tokens expire after 7 days and users must re-authenticate. This is acceptable for internal applications but increases friction for active users. No account lockout after failed login attempts, though rate limiting provides some defense. No password reset functionality. Email verification on registration is absent, so any email can be registered without proof of ownership.

JWT_SECRET is read from environment but defaults to 'your-secret-key' if unset, which is insecure. The warning log helps but doesn't prevent the server from starting with a weak secret. Recommend failing startup if JWT_SECRET is weak in production.

Auth endpoints have input validation via validateRegistration middleware, but other endpoints (task creation, schedule creation, staff management) lack structured validation despite the plan identifying Joi validators as Priority 1. The validator npm package is installed but no Joi schemas exist in the codebase.
